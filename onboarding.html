Maintaining FinancePlanner

First steps

  1. Open README.md for the project conventions and entry point.
  2. Run the app by opening index.html directly in a modern browser. There is no build step or package install.
  3. Explore the People and data tab. Export a JSON backup before testing destructive data changes; the sample files in data/ can be imported for realistic data.
  4. For account-related work, read the page collaborators: accounts-controller.js, accounts-view.js, accounts-service.js, accounts-constants.js, app.js, household-planner-model.js, and persistence.js.

Privacy boundary: household data is stored in this browser’s local storage and the app does not upload it. The exchange-rate service makes a separate request to open.er-api.com; do not add personal financial data to that request.

How the app is put together

This is a small, dependency-free browser application. Scripts are classic scripts wrapped in IIFEs; they publish shared APIs on window rather than using a module bundler. Keep the script order in index.html aligned with those dependencies.

App shell

app.js loads and saves state, owns navigation, assembles the shared page context, renders the selected page, and coordinates updates.

Shared calculations

The model converts currencies and derives account, debt, goal, and budget summaries. Views should display these results rather than reimplementing totals.

Shared UI and helpers

DOM helpers, UI primitives, and table editor provide common rendering and editing behavior.

Page controllers

Each page under src/js/pages/ is split into <pagename>-controller.js (page actions and coordination), <pagename>-view.js (DOM rendering), <pagename>-service.js (state operations and calculations), and, when needed, <pagename>-constants.js (page-specific static values). Shared constants live in src/js/shared/constants/. Scripts receive shared helpers through the app context.

Persistence and FX

Persistence handles browser storage, defaults, and normalization. Exchange rates fetches provider rates and reports status.

App shell markup and styles

index.html defines the navigation and main-content mounts and script order; the stylesheet owns responsive layout, themes, and component styles.

Script load order

The shell loads the model and DOM utility first, followed by persistence, exchange rates, shared UI/table components, then each page’s service, view, and controller, followed by app.js. Controllers register factories before the app constructs them; dependencies arrive through a context object.

Accounts page: responsibilities and behavior

accounts-controller.js registers HouseholdPlannerPages.accounts(context) and returns a render function. The view builds account and set-aside editing UI; the service owns account filtering, currency conversion, and account/commitment state operations.

Currency conventions

  • state.fx.php is PHP per 1 NZD, so a PHP amount converts to NZD by dividing by this rate.
  • state.fx.usd is NZD per 1 USD, so a USD amount converts to NZD by multiplying by this rate.
  • NZD is the default currency and converts at 1. Keep input labels, display labels, model math, and import normalization consistent if adding a currency.
  • Changing an account’s currency or moving a commitment to another account adjusts its stored amount using the old/new NZD rates, preserving its NZD value when both rates are valid.

Editing and refresh conventions

Most account fields are created with the app’s field() helper. It updates the backing state, runs any field-specific onChange, then calls commit(). A commit invalidates calculated summaries, saves state, and refreshes the rendered calculated values. New rows use uid(), markDirty(), and commit(); deletions should preserve the existing confirmation and relationship-cleanup behavior.

State, calculations, and data safety

  • The primary state is an object containing collections such as users, accounts, commitments, debts, goals, and transactions, plus fx and ui.
  • Persistence uses the key household-planner-v1. Theme choice is stored separately. Defaults and old-data normalization live in the persistence service.
  • Account summaries are derived by HouseholdPlannerModel.compute(state, asOf). Account values are converted to NZD; net is balance less liabilities; free is net less commitments.
  • Commitments use target IDs such as debt:<id> and goal:<id>. The app’s detach() helper handles references when linked records are removed. Check this behavior before changing deletion paths.
  • Export/import is JSON-based. Normalization supports missing fields and legacy stored formats; the current saved-data build marker is updated by save(). If a state-shape change needs migration, update normalization and test both old and current data.
  • Browser storage can be unavailable or full. The shell reports when saving is unavailable; avoid making UI changes appear persisted when save did not succeed.

The data-management UI is implemented in data-view.js, with actions coordinated by data-controller.js. A downloaded export is a sensitive backup: treat it like the household’s financial records.

Safe change workflow

  1. Trace the feature. Follow the path from the page renderer to its context helpers and then to model/persistence behavior. Search for the state fields and shared helper before introducing a second implementation.
  2. Keep ownership clear. Put page-specific interactions in the page controller, reusable presentation in shared components, calculations in the model, and storage/migration logic in persistence.
  3. Preserve state and relationship rules. Account removal currently removes its commitments and clears transaction account references. Debt/goal removal reclassifies linked commitments. User removal clears owner references.
  4. Use existing rendering patterns. Build DOM with the existing helpers, use data-calc plus an _u() updater for values that change after commits, and use esc() when inserting user-provided text into HTML.
  5. Keep docs and browser behavior aligned. Update the relevant page copy or README when a user-facing workflow or developer convention changes.
Current worktree note: the existing working tree includes an uncommitted edit in app.js that enables error handling for JSON import parsing. Do not overwrite or revert it while making unrelated changes.

Validation checklist

No automated test files or build configuration were found in the repository at the time this guide was written. For a change, run the app directly in a browser and verify the affected flow, plus the relevant checks below.

  • Open index.html; check the browser console for script errors and confirm all tabs render.
  • For account edits, add an account, change owner/currency/balance/liabilities, and confirm the account summary and dashboard totals update.
  • For commitments, add/edit/delete a line; try linking it to a debt or goal; verify account filtering and NZD aggregate totals.
  • For currency logic, check PHP (division), USD (multiplication), and NZD (unchanged); test a currency/account change with saved amounts.
  • Delete an account with linked records and confirm the expected cleanup. Use exported sample/test data so real browser data is not at risk.
  • Test manual rate entry and provider refresh when network access is available. Confirm status feedback and that stored rates remain usable when refresh fails.
  • Export JSON, import it into a disposable browser profile or after a backup, then verify the app restores the state. Also check the responsive layout and light/dark appearance.

For future automated coverage, prioritize isolated model cases for conversion/summary calculations and browser-level flows for import/export and account/commitment editing.
